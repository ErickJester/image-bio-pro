## Conceptos nuevos

### La terminal

Una ventana donde se le dan órdenes escritas a la computadora: instalar programas, ejecutar código, usar Git. En VS Code se abre con `` Ctrl + ` ``. En Windows es PowerShell.

### Python y sus versiones

En la computadora ya estaba Python 3.14, pero el proyecto usa **3.12** porque:

- Es la versión que trae Ubuntu, el sistema del servidor (VPS). Lo que funcione aquí funcionará igual allá.
- Es la más probada con las librerías que vamos a usar: OpenCV, PyTorch y YOLO.

En Windows se pueden tener varias versiones instaladas. El comando `py` permite elegir cuál usar: `py -3.12` usa la 3.12 y `py -3.14` la 3.14.

### Entorno virtual (`venv`)

Una carpeta dentro del proyecto (`.venv`) con **su propio Python y sus propias librerías**, separadas del resto de la computadora. Es como una caja de herramientas exclusiva del proyecto.

No es obligatorio, pero en este proyecto evita problemas reales:

1. **En el servidor no hay opción.** Ubuntu bloquea instalar librerías con `pip` en el Python del sistema (error `externally-managed-environment`). Allá se necesita un venv sí o sí, así que conviene trabajar igual desde el principio.
2. **Otros proyectos no se rompen.** Si este proyecto necesita una versión de una librería y otro proyecto necesita otra, instaladas en el mismo Python una rompe a la otra. Con un venv por proyecto, cada uno tiene sus versiones.
3. **Se sabe exactamente qué usa el proyecto.** Lo instalado en el venv es lo único que tiene el proyecto. Con `pip freeze > requirements.txt` se saca la lista exacta, y en el servidor se reinstala igual con un comando.
4. **Si algo se descompone, se borra y listo.** Se borra `.venv`, se vuelve a crear y se reinstala. El Python principal no se toca.
5. **Queda amarrado a la versión correcta.** El venv usa Python 3.12; dentro de él basta con escribir `python`, sin `py -3.12`.

Alternativas que hacen algo parecido: **conda** (popular en ciencia de datos, más pesada), **uv** (moderna y rápida) y **Docker** (aísla todo el sistema; demasiado para este proyecto). Se eligió `venv` porque ya viene con Python y es lo que se usará en el servidor.

### `pip` y `requirements.txt`

`pip` instala librerías dentro del entorno virtual activo. `requirements.txt` es la lista de librerías del proyecto; con `pip install -r requirements.txt` cualquier computadora instala lo mismo.

### `.gitignore`

La lista de archivos y carpetas que Git no debe subir. Aquí importa por dos razones: el entorno virtual pesa cientos de MB y se puede recrear, y **las imágenes del cliente no se suben al repositorio**.

### Política de ejecución de PowerShell

Por seguridad, Windows trae PowerShell configurado para no ejecutar scripts (archivos `.ps1`). El script que activa el venv es uno de ellos, así que hay que permitirlo una vez. Ver el error del día en [`errores.md`](errores.md).

## Comandos que usé

```powershell
# 1. Instalar Python 3.12 y comprobarlo (cerrar y reabrir la terminal entre ambos)
winget install Python.Python.3.12
py -3.12 --version

# 2. Crear el entorno virtual con Python 3.12
py -3.12 -m venv .venv

# Permitir scripts locales en PowerShell (solo una vez, para mi usuario)
Set-ExecutionPolicy -Scope CurrentUser RemoteSigned

# Activar el entorno virtual: aparece (.venv) al inicio de la línea
.venv\Scripts\Activate.ps1
```

Cada vez que se abra una terminal nueva hay que volver a activar el entorno con `.venv\Scripts\Activate.ps1`.
